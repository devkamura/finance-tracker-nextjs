# 家計簿アプリ 要件定義書
## レシート・明細・支出分析・2人の精算・分類支援

---

# 1. アプリの目的

本アプリは、**2人で利用する家計簿アプリ**である。

単に「誰がいくら払ったか」を記録するだけではなく、以下を目的とする。

1. 毎月の支出をカテゴリ別に分析する
2. 2人の共同生活・共同活動にいくら使ったかを把握する
3. 各ユーザーが本来負担すべき金額を算出する
4. 各ユーザーが実際に支払った金額を把握する
5. 個人立替額を把握する
6. 最終的に、どちらがどちらにいくら支払えば公平になるのかを算出する
7. フィルタを使用して、任意の支出の合計金額を算出できるようにする
8. 月ごとの支出推移を確認し、支出削減・家計改善に活用する
9. 支出の分類に迷った場合に、ルールに沿って対話的に分類できるようにする
10. レシートを画像として保存し、紙のレシートを管理する負担を減らす

---

# 2. ユーザー・グループ管理

本アプリは、**1つのグループを2人で利用することを前提**とする。

## 2.1 ユーザー数の上限

1グループに登録できるユーザーは、**管理者を含めて最大2人**とする。

```text id="q1d4p8"
1グループ
├─ 管理者（User A）
└─ 一般ユーザー（User B）
```

3人以上のユーザーを同一グループに登録することはできない。

---

## 2.2 管理者

グループを作成したユーザーを管理者とする。

管理者は、グループに所属するユーザーを管理できる。

### 管理者ができること

- 一般ユーザーの登録
- 一般ユーザーの削除
- グループ情報の管理
- その他、管理者権限が必要な操作

---

## 2.3 ユーザー登録

管理画面からユーザーを登録できる。

ただし、すでに2人のユーザーが登録されている場合は、新たなユーザーを登録できない。

### 例

```text id="6g5z2k"
現在の登録人数：1人
→ 2人目を登録可能

現在の登録人数：2人
→ 3人目は登録不可
```

登録画面では、現在の登録人数を考慮して登録可否を制御する。

---

## 2.4 2人利用を前提とした精算

本アプリの精算機能は、**2人での共同生活を前提**として設計する。

そのため、「共同」の支出は常に2人で折半する。

```text id="l7a8xq"
共同支出 10,000円

User A：5,000円
User B：5,000円
```

3人以上での分割計算は初期仕様では対象外とする。

---

# 3. 基本的な考え方

支出を以下の4つの軸に分離して管理する。

| 項目 | 意味 |
|---|---|
| **カテゴリ** | 何にお金を使ったか |
| **目的** | 誰との・何のために発生した支出か |
| **支払者** | 実際にお金を支払ったユーザー |
| **帰属先** | 最終的に誰の負担として扱うか |

これらは別の概念として扱う。

### 例

ユーザーAがユーザーBと映画に行き、2人分6,000円を支払った。

```text id="a4s6n2"
カテゴリ：交際費
目的：生活維持
支払者：ユーザーA
帰属先：共同
支払額：6,000円
```

---

# 4. カテゴリ

カテゴリは、

> **「何にお金を使ったか」**

を表す。

カテゴリ例：

- 食費
- 日用品
- 衣類・ファッション
- 交通費
- 通信費
- 賃料
- 水道光熱費
- 交際費
- 娯楽
- 宿泊・旅行
- 医療費
- 学習・自己投資
- その他

カテゴリは、月次・年間の支出分析に使用する。

---

# 5. 目的

目的は、

> **「誰との・何のために発生した支出か」**

を表す。

目的例：

- 生活維持
- 個人
- 仕事
- 家族
- 友人

「彼氏」「彼女」などの固定的な関係性ではなく、ユーザー名とは独立した分類軸として管理する。

---

# 6. 生活維持の定義

生活維持とは、単なる生活必需品を意味しない。

> **2人の共同生活・共同活動のために発生した支出**

を「生活維持」とする。

例えば、

- 2人分の食材
- 普段の2人の外食
- 日用品
- 賃料
- 水道光熱費
- Wi-Fi
- デートでの食事
- デートでの映画
- デートでの交通費
- 2人での旅行
- 2人での宿泊

などを含む。

---

# 7. 支出カテゴリと目的の判定基準

「カテゴリ」は支出の種類、「目的」は支出の相手・目的として判断する。

| 支出内容 | カテゴリ | 目的 |
|---|---|---|
| 自炊用の食材 | 食費 | 生活維持 |
| 普段の外食 | 食費 | 生活維持 |
| デートでの食事 | 交際費 | 生活維持 |
| 友人との食事 | 交際費 | 友人 |
| 自分だけの外食 | 食費 | 個人 |
| デートで映画 | 交際費 | 生活維持 |
| 友人と映画 | 交際費 | 友人 |
| 一人で映画 | 娯楽 | 個人 |
| デートでの交通費 | 交通費 | 生活維持 |
| 友人との交通費 | 交通費 | 友人 |
| 一人の交通費 | 交通費 | 個人 |
| デートでの宿泊 | 宿泊・旅行 | 生活維持 |
| 2人の旅行の宿泊 | 宿泊・旅行 | 生活維持 |
| 友人との旅行の宿泊 | 宿泊・旅行 | 友人 |
| 一人旅の宿泊 | 宿泊・旅行 | 個人 |

### 重要なルール

**デートだから必ず「交際費」になるわけではない。**

例えば、

- デートでの食事 → 交際費
- デートでの映画 → 交際費
- デートでの交通費 → 交通費
- デートでの宿泊 → 宿泊・旅行

とする。

旅行・宿泊など独立して分析したいカテゴリは、そのカテゴリを優先する。

---

# 8. レシートと明細を分離する

家計簿は「レシート」と「明細」を分けて管理する。

## レシート

1回の会計を表す。

保持する情報：

- レシートID
- 日付
- 店舗
- 支払者
- 支払額
- レシート画像

## 明細

レシート内の商品・サービスを表す。

保持する情報：

- 商品名
- 金額
- 税区分
- 税率
- カテゴリ
- 目的
- 帰属先

---

# 9. レシート画像管理

レシートには、**レシート画像を紐付けて保存できるようにする。**

レシート画像の保存とOCR処理は別機能として扱う。

```text id="n3j2hx"
レシート画像の保存
≠
OCRによる情報抽出
```

ユーザーは、OCRを利用せずにレシート画像だけを保存することもできる。

---

# 10. レシート画像アップロード

### OCRを利用する場合

```text id="q4d1yt"
レシート画像をアップロード
        ↓
画像をレシートに保存
        ↓
OCR処理
        ↓
商品名・金額等を抽出
        ↓
レシート・明細データを作成
```

OCRを実行した場合は、**OCR処理に使用した元画像を自動的にレシートへ保存する。**

### OCRを利用しない場合

```text id="x7e3pa"
レシート画像をアップロード
        ↓
画像のみ保存
        ↓
OCR処理は実行しない
```

必要に応じて後から手動で明細等を登録できるようにする。

---

# 11. レシート画像の利用目的

- 後からレシート内容を確認する
- OCR結果に誤りがないか確認する
- 明細を確認する
- 金額を確認する
- 家計簿登録後の証跡として残す
- 紙のレシートを保管する手間を減らす

---

レシート詳細画面から、保存されているレシート画像を確認できるようにする。

```text id="p5w8ye"
2026/08/31
○○スーパー

支払額：3,500円

明細
----------------
食費       2,000円
日用品     1,000円
個人          500円

[ レシート画像を見る ]
```

# 13. 1つのレシートに複数の帰属先を許容する

1回の買い物で、

- 共同のもの
- ユーザーA個人のもの
- ユーザーB個人のもの

が混在することを許容する。

---

# 14. 支払者と帰属先を分離する

### 支払者

> 実際にお金を払ったユーザー

### 帰属先

> 最終的にその支出を誰の負担として扱うか

例えば、ユーザーAがユーザーBの日用品を購入した場合、

```text id="u8e2mc"
支払者：A
帰属先：B
金額：5,000円
```

となる。

これは、

> **AがBの支出を立て替えた**

と扱う。

---

# 15. 帰属先「共同」の扱い

帰属先が「共同」の場合、その支出は2人で折半する。

```text id="f4n6zr"
共同支出：10,000円

A負担：5,000円
B負担：5,000円
```

---

# 16. ユーザー別負担額

各ユーザーの負担額は、帰属先を基準として計算する。

- 共同 → 1/2
- ユーザーA → 100% A
- ユーザーB → 100% B

---

# 17. ユーザー別実支払額

実支払額は、

> **実際にそのユーザーが支払った金額**

を集計する。

帰属先による折半は行わない。

### 例

共同支出10,000円をAが全額支払った場合、

| | A | B |
|---|---:|---:|
| 負担額 | 5,000円 | 5,000円 |
| 実支払額 | 10,000円 | 0円 |

---

# 18. 個人立替

支払者と帰属先が異なる場合、立替が発生する。

### 例

AがBの個人商品5,000円を支払った。

```text id="g9k3zs"
支払者：A
帰属先：B
金額：5,000円
```

AがBのために5,000円立て替えたものとして扱う。

---

# 19. 最終精算

最終精算では、

- 各ユーザーの本来の負担額
- 各ユーザーの実支払額

を比較する。

基本式：

```text id="j5q0mu"
精算差額
＝ 実支払額 − 本来の負担額
```

差額をもとに、最終的な精算額を表示する。

---

# 20. 税込・税別

明細ごとに税区分を管理する。

ユーザーが明細登録時に、

- 税込
- 税別

を選択する。

税別の場合、税率もユーザーがプルダウンから選択する。

**税率をOCR・AI・システムが推定して確定してはならない。**

### 税込の場合

レシートに記載された税込金額を使用する。

### 税別の場合

ユーザーが選択した税率を使用する。

端数処理は現時点では切り捨てとする。

---

# 21. 明細合計と支払額は一致しなくてよい

以下の理由などにより、

> **支払額 ≠ 明細金額の合計**

となることを許容する。

- PayPayポイント
- クーポン
- ポイント利用
- レジ値引き
- セット割引
- 税計算・端数処理
- その他の値引き

ポイントやクーポンの詳細な帰属先を管理する必要はない。

---

# 22. 支払額を精算の基準とする

精算では、

> **実際の支払額を正とする。**

例えば、

```text id="v2k8qs"
支払額：1,700円
明細合計：2,000円
```

であっても、精算の基準は1,700円とする。

個人明細の合計が実支払額を超える場合は、実支払額を上限として扱い、可能であれば「要確認」と表示する。

---

# 23. 支出分類支援機能「お助け」

ユーザーがカテゴリ・目的・帰属先の判断に迷った場合に使用できる、

> **「お助け」機能**

を提供する。

通常の支出登録では、ユーザーがカテゴリ・目的・帰属先を直接選択する。

迷った場合のみ「お助け」ボタンを押す。

---

# 24. お助け機能の基本方針

基本的には、

> **アプリに定義された分類ルールに沿って、Yes / No形式で対話的に分類する。**

AIに毎回分類を任せない。

---

# 25. 分類ルールベース

```text id="s2n6bw"
条件
 ↓
質問
 ↓
Yes → 次のルール
No  → 別のルール
 ↓
最終的なカテゴリ・目的・帰属先
```

---

# 26. お助け機能とGemini

通常の分類ではGemini APIを呼び出さない。

```text id="p8j2cc"
通常
 ↓
ルールベース

ユーザーが迷った
 ↓
「お助け」
 ↓
Yes / Noによるルール判定

ルール不足・未知のケース
 ↓
必要な場合のみGemini
```

これにより、APIコストを抑えつつ、分類結果の一貫性を維持する。

---

# 27. OCRと分類の分離

OCRでは分類を行わない。

OCRの役割は、

> **レシートから商品名・金額などの情報を取得すること**

に限定する。

```text id="m8x6rp"
レシート画像
 ↓
OCR
 ↓
商品名・金額
 ↓
家計簿登録
 ↓
分類
```

---

# 28. 月次集計

月次集計は**暦月単位**とする。

> **5月の集計 = 5月1日〜5月31日に発生した支出**

「本日から過去30日」ではない。

月次集計では、

- カテゴリ別支出
- 目的別支出
- ユーザー別負担額
- ユーザー別実支払額
- 個人立替額
- 最終精算額
- 総支出額

を確認できるようにする。

---

# 29. 月次カテゴリ別集計

例えば8月の支出を、

```text id="q6s8y3"
食費          40,000円
日用品        10,000円
交際費        20,000円
通信費         5,000円
賃料          20,000円
水道光熱費     8,000円
宿泊・旅行    30,000円
```

のように表示する。

---

# 30. 過去12か月の支出推移

過去12か月の月次支出額を時系列で確認できるようにする。

基本的には折れ線グラフを使用する。

横軸：

> 月

縦軸：

> 支出額

# 31. 年間推移グラフの切り替え

分析対象を切り替えられるようにする。

例えば、

- 総支出
- 食費
- 日用品
- 交際費
- 交通費
- 宿泊・旅行
- その他のカテゴリ
- 生活維持支出
- ユーザーA負担額
- ユーザーB負担額

など。

# 32. 任意のフィルタによる集計

履歴画面では、ユーザーが条件を自由に指定し、該当する支出の合計金額を確認できるようにする。

### フィルタ条件例

- 日付・期間
- 支払者
- カテゴリ
- 目的
- 帰属先
- 店舗
- ユーザー

複数条件を組み合わせて検索できるようにする。

---

# 33. 任意集計の具体例

### 賃料＋水道光熱費

```text id="7d5g4w"
カテゴリ：
・賃料
・水道光熱費
```

→ 合計額を表示。

### 生活維持の交際費

```text id="q3p9am"
目的：生活維持
カテゴリ：交際費
```

→ 合計額を表示。

### ユーザーAの負担額

```text id="c6k2zx"
対象：ユーザーA
期間：2026年8月
集計方法：負担額
```

共同分についてはAの負担分として1/2を計上する。

### ユーザーAの実支払額

```text id="t9h5df"
支払者：ユーザーA
期間：2026年8月
集計方法：実支払額
```

実際にAが支払った金額をそのまま集計する。

# 35. データモデル概念

概念的には以下を想定する。

```text id="v7p4qd"
Group
├─ id
├─ name
└─ ...

User
├─ id
├─ name
└─ ...

GroupMember
├─ group_id
├─ user_id

```

`GroupMember`の登録数は**1グループにつき最大2件**とする。

```text id="x2r9fk"
Receipt
├─ id
├─ group_id
├─ date
├─ store
├─ payer_user_id
├─ amount（実支払額）
└─ receipt_image
```

```text id="z5c8nm"
ReceiptDetail
├─ id
├─ receipt_id
├─ item_name
├─ amount
├─ tax_type
├─ tax_rate
├─ category_id
├─ purpose_id
└─ owner_user_id
```

`owner_user_id` は帰属先を表す。

- 特定のUser → そのユーザー個人
- NULL等 → 共同

という実装方法を検討する。
