開発環境の準備、本番環境の設定、本番リリースの手順、ローカルのテストデータをまとめた文書。

## 1. 全体像

```text
ブラウザ
  │  ①「Googleでログイン」
  ▼
Next.js（Vercel）
  │  ② signInWithOAuth() で Supabase の /authorize へリダイレクト
  ▼
Supabase Auth（Supabase プロジェクト）
  │  ③ Google へリダイレクト（Supabase Auth 自身の Google クライアント設定を使う）
  ▼
Google OAuth 同意画面
  │  ④ 許可後、Supabase Auth のコールバックへ戻る
  ▼
Supabase Auth → Next.js の /auth/callback へリダイレクト
  │  ⑤ セッションを確立してログイン完了
  ▼
以降のデータはすべて Supabase（Postgres・Storage）に保存する
```

- Google との通信はこのログインの流れだけ。Google の設定は `supabase/config.toml` 経由で Supabase プロジェクトに登録する（Vercel の環境変数とは別）
- 以前あった Google Drive への保存は廃止した。Drive 関連の設定（`drive.file` スコープ・Drive API の有効化・`GDRIVE_FOLDER_ID`）は不要
- レシート画像の読み取りは、サーバーから Gemini API を呼ぶ（`GEMINI_API_KEY`）

## 2. 開発環境

### 2.1 起動

```bash
npm install
supabase start        # ローカルの Supabase（Docker）。初回は migrations と seed.sql を自動で流す
cp .env.example .env   # supabase status の値などを設定する（2.2節）
npm run dev
```

- Next.js は Docker を使わず、ローカルの Node.js で起動する（Docker はローカルの Supabase だけで使う。本番は Vercel のため、docker-compose のファイルは持たない）
- ローカルの Supabase のポート：API `55321`、DB `55322`（`supabase status` で確認できる）
- DB を作り直すとき：`supabase db reset`
- 型の再生成：`supabase gen types typescript --local > lib/supabase/database.types.ts`

### 2.2 環境変数（`.env`）

| 変数 | 内容 |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` | `supabase status` の Project URL・Publishable key |
| `SUPABASE_SERVICE_ROLE_KEY` | Secret key。今のアプリのコードからは使っていない（`lib/supabase/admin.ts` に用意してあるだけ）。ブラウザに出さない |
| `NEXT_PUBLIC_SITE_URL` | アプリの URL（OAuth のコールバックの組み立てに使う） |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | ログイン用の OAuth クライアント。`supabase/config.toml` の `[auth.external.google]` が `env()` で読むので、`supabase start` の前に設定しておく |
| `GEMINI_API_KEY` | 画像の読み取り（Gemini API）。サーバー専用 |

### 2.3 テスト

```bash
npm test                   # 単体テスト（Vitest）
npm run test:integration   # 結合テスト（ローカルの Supabase に接続。supabase db reset した状態で行う）
npm run lint
npm run build
```

- 外部 API（Gemini など）を呼ぶテストは、必ずモックにする
- E2E は自動化していない。Issue ごとの受け入れテスト仕様書で手動確認する

## 3. 本番環境の設定

### 3.1 Google Cloud Console

**OAuth クライアント**：開発用・本番用で別々に作る（片方が漏れたり失効したりしても、もう片方に影響しないようにするため）。

1. [Google Cloud Console](https://console.cloud.google.com/) →「APIとサービス」→「認証情報」→「認証情報を作成」→「OAuthクライアントID」
2. アプリケーションの種類：**ウェブアプリケーション**
3. 承認済みのリダイレクト URI に、Supabase のコールバック URL を登録する
   - ローカル：`http://127.0.0.1:55321/auth/v1/callback`
   - 本番：`https://<本番プロジェクトref>.supabase.co/auth/v1/callback`
4. 発行されたクライアント ID・シークレットを控える（`supabase config push` で使う。Vercel には設定しない）

**OAuth 同意画面**（プロジェクト共通で1回だけ）：「APIとサービス」→「Google Auth platform」。

- 公開ステータスが「テスト」のときは、「Audience」の「Test users」に、ログインする Google アカウントを追加する（追加していないアカウントはログインできない）
- スコープは `openid`・`email`・`profile` だけでよい

### 3.2 Supabase

| 名称 | 用途 | 取得場所 |
|---|---|---|
| Project URL | `NEXT_PUBLIC_SUPABASE_URL` | `https://【ref】.supabase.co`（ダッシュボードの URL の ref） |
| Project ref | `supabase link` でプロジェクトと紐づける | 「Project Settings」の「Reference ID」 |
| Publishable key（旧 anon key） | `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 「Project Settings」→「API Keys」 |
| Secret key（旧 service_role key） | `SUPABASE_SERVICE_ROLE_KEY`（任意） | 同上。**ブラウザに出さない** |
| Personal Access Token（`sbp_...`） | Supabase CLI の認証（`SUPABASE_ACCESS_TOKEN`）。アプリの実行には使わない | アカウント設定 → Access Tokens |

**マイグレーション・マスタの反映**

```bash
supabase link --project-ref <本番プロジェクトref>
supabase db push --linked --include-seed   # seed.sql（取引種別・税率・カテゴリ）も反映する。seed は冪等
```

**Google 認証の設定の反映**：`config.toml` の `[auth.external.google]` は、`supabase config push` を実行したときのシェルの環境変数から値を読む。`additional_redirect_urls` に本番の `/auth/callback`（例：`https://finance-tracker-nextjs-two.vercel.app/auth/callback`）を入れてから実行する。

```bash
set -a; source .env.prod; set +a   # 本番の GOOGLE_CLIENT_ID・GOOGLE_CLIENT_SECRET を含むファイル
supabase config push
```

### 3.3 Vercel

1. GitHub のリポジトリを「Add New」→「Project」で取り込む（Framework は Next.js）
2. 「Project Settings」→「Environment Variables」に設定する

| 変数 | 値 |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 3.2節 |
| `NEXT_PUBLIC_SITE_URL` | Vercel の本番の URL |
| `GEMINI_API_KEY` | Google AI Studio で発行 |
| `SUPABASE_SERVICE_ROLE_KEY` | 任意（今は使っていない） |

- タイムゾーン（JST）は環境変数では設定しない（`TZ` は Vercel の予約変数）。`instrumentation.ts` で設定している。これがないと、日時が9時間ずれる
- 環境変数を変えたら、「Deployments」→ 最新のデプロイの「Redeploy」で反映する（自動では反映されない）

### 3.4 新しい環境を作るとき

1. OAuth クライアントを発行し、リダイレクト URI に `https://<ref>.supabase.co/auth/v1/callback` を登録する
2. Supabase プロジェクトを作る
3. `supabase link` → `supabase db push --include-seed`
4. `config.toml` の `additional_redirect_urls` に、その環境の URL を追加する
5. `supabase config push`（その環境の `GOOGLE_CLIENT_ID`・`GOOGLE_CLIENT_SECRET` を環境変数に入れて実行）
6. Vercel に環境変数を設定してデプロイする

### 3.5 トラブルシューティング

| 症状 | 原因 |
|---|---|
| ログイン後に `/login?error=auth` に戻る | `config.toml` の `site_url`・`additional_redirect_urls` と `NEXT_PUBLIC_SITE_URL` が一致していない。`localhost` と `127.0.0.1` は別のホストとして扱われ、Cookie も共有されない |
| ログイン後、エラーなしでログイン画面に戻る | `NEXT_PUBLIC_SITE_URL` が空、または `/auth/callback` を通らずに `/?code=...` に着いている |
| Google で「アクセスをブロックされました」 | 同意画面が「テスト」で、そのアカウントがテストユーザーにない |
| Vercel の環境変数を変えても反映されない | Redeploy が必要 |

## 4. 本番リリース

**マイグレーションを先に本番 DB へ反映し、その後に dev → main をマージする。** 逆にすると、新しいアプリがまだない列・テーブルを読んで本番が落ちる。

### 4.1 リリース前（dev ブランチで）

- [ ] リリースに含める Issue のブランチが、すべて dev にマージされている
- [ ] `npm test`・`npm run test:integration`（`supabase db reset` した DB で）・`npm run lint`・`npm run build` が通る
- [ ] `supabase gen types typescript --local` の結果が `lib/supabase/database.types.ts` と一致する
- [ ] 含める Issue の受け入れテスト仕様書の項目がすべて OK
- [ ] 精算画面の金額が、リリース前と変わっていない（精算に関わる変更がないとき）

### 4.2 本番 DB の確認とバックアップ

```bash
set -a; source .env.prod; set +a     # SUPABASE_DB_PASSWORD（本番 DB のパスワード）
supabase migration list --linked     # 未適用が今回の分だけか
supabase db dump -f prod-schema.sql
supabase db dump --data-only -f prod-data.sql
```

- `SUPABASE_ACCESS_TOKEN` は `~/.zshrc` に、`SUPABASE_DB_PASSWORD` は `.env.prod` に置く
- Supabase CLI はグローバルの v2 を使う（npx の v3 は config のエラーになる）
- バックアップのファイルはリポジトリにコミットしない（個人の家計データのため）。ダッシュボードの「Database → Backups」にも直近のバックアップがあるか確認する
- データを書き換えるマイグレーションは、本番 DB で `begin; …; rollback;` で流してエラーがないか確かめる（psql の接続先は `supabase/.temp/pooler-url`、パスワードは `PGPASSWORD`）。書き換える件数も控えておく

### 4.3 反映

- [ ] `supabase db push --linked --yes`（`seed.sql` が変わったときだけ `--include-seed`）
- [ ] `supabase migration list --linked` で適用済みになっている
- [ ] dev → main の PR（タイトルは `release: …`）をマージし、Vercel の「Deployments」でデプロイの成功を確認する
- [ ] 環境変数の追加・変更が要るときは、デプロイの前に Vercel に設定する

### 4.4 反映後の確認（本番の画面で）

- [ ] Google でログイン・ログアウトできる
- [ ] レシートの登録・編集・一覧・詳細、分析画面、精算画面が表示できる
- [ ] 今回の Issue の変更点が動く
- [ ] Vercel の「Logs」にエラーがない

### 4.5 問題が起きたとき

- アプリ：Vercel の「Deployments」で1つ前のデプロイを「Promote to Production」で戻す。ただし DB は新しいままなので、テーブル・列を削除したマイグレーションの後は古いアプリに戻せないことがある。その場合は新しいアプリを直して出し直す
- DB：マイグレーションは自動では戻らない。新しいテーブル・列は使わなければ古いアプリに影響しないので、基本はアプリだけ戻して DB は残したまま直す。最後の手段として 4.2節のバックアップから復元する（反映後に登録されたデータは失われる）

## 5. ローカルのテストデータ

`supabase/snippets/` に、ローカルで画面を確かめるためのデータを入れる SQL がある。**グループ・ユーザーの ID はローカル環境のもの。本番では絶対に流さない。** メンバーは **ゆうき**（管理者）と **ふみ**（一般メンバー）、グループは「ぽてぽて」。

```bash
PGPASSWORD=postgres psql -h 127.0.0.1 -p 55322 -U postgres -d postgres -f supabase/snippets/<ファイル名>
```

| ファイル | 内容 |
|---|---|
| `analytics-dummy-data.sql` | 分析の集計の確認用。ユーザー・グループ以外のデータを消して入れ直す（5.1節） |

#### 集計の計算方法

| ルール | 内容 | このデータでの例 |
|---|---|---|
| 按分 | 支払額が明細の合計と違うときは、支払額を明細の金額（税別の明細は税込に直した金額）の比率で分ける。1円未満は切り捨て、余った円は金額の大きい明細から1円ずつ足す | No.12：44,000＋11,000＝55,000 を支払額 49,500 で分ける → 宿泊 49,500×44,000÷55,000＝39,600、夕食 9,900。<br>No.13：1,521×156÷1,520＝156.1→156、1,521×264÷1,520＝264.1→264、1,521×1,100÷1,520＝1,100.7→1,100。合計 1,520 で1円余るので、金額の最も大きい洗剤に足して 1,101 |
| 税別 | 税別の明細は、明細ごとに税率を掛けて税込にする（1円未満は切り捨て） | No.13：145×1.08＝156.6→156、245×1.08＝264.6→264、1,000×1.10＝1,100 |
| 返金 | 返金のレシートはマイナスで集計する。合計がマイナスになったカテゴリは、円グラフには描かず、表と注意書きに出す | No.17：6月の衣類は −5,000 |
| 表示対象 | 全体＝すべて。ゆうき（共同を含めない）＝帰属先がゆうきの明細。ゆうき（共同を含める）＝それ＋共同の明細の **1/2** | ゆうき（共同を含める）＋ふみ（共同を含める）＝全体 |
| ％ | その行の金額 ÷ 絞り込み後のプラスの行の合計（小数第2位を四捨五入） | 9月は合計 100,000 なので、金額 ÷ 1,000 |
| 費用区分 | 明細ごとには持たず、今のカテゴリの設定で集計する | 学習・自己投資は固定費 |
