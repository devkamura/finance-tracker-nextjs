アプリ全体の「今の設計」をまとめた文書。画面ごとに利用者ができることは [画面仕様書/](./画面仕様書/README.md)、要件は [要件定義書.md](./要件定義書.md)、金額の算出方法は [用語と算出方法.md](./用語と算出方法.md) にある。Issue ごとの設計は `docs/仕様書/#NN_タイトル/詳細設計書.md` に書き、完了時にこの文書へ反映する。

## 1. 全体構成

### 1.1 技術構成

| 区分 | 採用 |
|---|---|
| フレームワーク | Next.js 16（App Router・Server Components・Server Actions）、React 19 |
| DB・認証・ストレージ | Supabase（PostgreSQL・Auth（Google）・Storage）。権限は RLS で保証する |
| グラフ | Recharts |
| アイコン | Font Awesome（CSS はルートのレイアウトで最初から読み込む） |
| 画像の読み取り | Gemini API（`@google/genai`） |
| テスト | Vitest（単体・結合。結合はローカルの Supabase に接続） |
| ホスティング | Vercel（本番）。開発はローカルの Supabase（Docker） |

- `googleapis` は依存に残っているが、Google Drive への保存を廃止したため使っていない
- Next.js 16 では middleware の規約が `proxy` に変わった。`proxy.ts` でセッションを更新する

### 1.2 処理の流れ

```text
画面（Server Component）
  └ lib/**/queries.ts（server-only）で Supabase から取得 → 画面用の型に変換して渡す
画面の操作（Client Component）
  └ 書き込みは lib/actions/*.ts（Server Action）→ 入力の検証 → Supabase（RLS・トリガーで再検証）
分析・一覧の絞り込み
  └ 開いたときに1回だけ取得し、以降の切り替えは画面の中の純粋関数で再計算する（サーバー通信なし）
```

- 計算ロジック（按分・精算・集計・絞り込み・既定値の適用）は、DB や画面に依存しない純粋関数にして単体テストで確かめる
- 分析と一覧の絞り込みは、同じ関数（`lib/analytics/dimensions.ts`・`aggregate.ts`・`drilldown.ts`）で明細の当てはまりと金額を決め、グラフの値と一覧の合計を必ず一致させる

### 1.3 時刻

- サーバーのタイムゾーンは `instrumentation.ts` で `Asia/Tokyo` に固定する（`TZ` は Vercel の予約変数で設定できないため、コードで設定する）
- 月は JST の暦月で判定する（`lib/analytics/months.ts`・`lib/receipts/queries.ts`）。日付の計算はサーバーで行い、ブラウザには `YYYY-MM`・`YYYY-MM-DD` の文字列だけを渡す
- `<input type="datetime-local">` の値は、サーバーのローカル時刻（JST）として解釈する

## 3. データベース

マイグレーションは `supabase/migrations/`、マスタの初期データは `supabase/seed.sql`、型は `lib/supabase/database.types.ts`（`supabase gen types` で生成）。

### 3.1 テーブル一覧

```text
auth.users ──1:1── profiles
groups ──< group_members（user_id は招待中なら NULL）
  ├──< receipts ──< receipt_details ──< receipt_detail_tags >── tags
  │      ├ payee_id → payees（NULL＝手入力）       ├ category_id → categories
  │      ├ transaction_type_id → transaction_types ├ breakdown_id → category_breakdowns（NULL＝内訳なし）
  │      └ payer_user_id / created_by → auth.users  ├ counterpart_id → counterparts
  │                                                 ├ tax_rate_id → consumption_taxes（税別のみ）
  │                                                 └ owner_user_id → auth.users（NULL＝共同）
  ├──< settlement_periods
  ├──< category_settings / category_breakdowns（categories ごと）
  ├──< counterparts / tags
  └──< payees ──< payee_aliases / payee_default_tags / payee_hidden_members
                 └──< payee_member_defaults ──< payee_member_default_tags
```

### 3.2 レシート・明細

**receipts**（1回の会計）

| 列 | 内容 |
|---|---|
| `group_id` | グループ |
| `payee_id` / `payee_name` | 支払い先。`payee_name` は表示用の名前（支払い先の名前を後で変えても過去のレシートの表示は変わらない）。手入力は `payee_id` が NULL |
| `transaction_type_id` | 支出／返金 |
| `occurred_at` | 会計の日時（timestamptz）。月の判定に使う |
| `payer_user_id` | 支払者。新規登録では登録者本人、編集で変更できる（2026-09-01 に `payer = created_by` の制約を外した） |
| `amount` | 支払額（実支払額）。0以上の整数。返金かどうかは取引種別で判定する |
| `receipt_image_path` | Storage 上の画像のパス（任意） |
| `is_duplicated` | 複製登録で作られたレシートか |
| `created_by` | 登録者 |

**receipt_details**（明細）

| 列 | 内容 |
|---|---|
| `item_name` / `price` | 商品名・価格（0以上の整数） |
| `tax_type` / `tax_rate_id` | 税込（`inclusive`、税率なし）／税別（`exclusive`、税率必須）。check 制約で対応を保証する |
| `category_id` / `breakdown_id` | カテゴリ・内訳。内訳がカテゴリとグループに合うかはトリガー（`check_receipt_detail_breakdown`）で確かめる |
| `counterpart_id` | 相手（必須）。グループのものかはトリガー（`check_receipt_detail_counterpart`）で確かめる |
| `owner_user_id` | 帰属先。NULL＝共同 |
| `is_special_expense` | 特別費（初期値 false） |

- 支払者・帰属先がグループのメンバーかは、DB の制約ではなくサーバーアクションで確かめる
- 明細のタグ（`receipt_detail_tags`）は、タグがグループのものかをトリガーで確かめる

### 3.3 精算（settlement_periods）

精算は都度計算し、**確定した月だけ**結果を保存する。

| 列 | 内容 |
|---|---|
| `period_month` | 対象月の1日。`(group_id, period_month)` で一意 |
| `status` | `confirmed`（確定。レシートをロックする）／`reopened`（再オープン中） |
| `user_a_*` / `user_b_*` | 確定時点のメンバー2人と、負担額・実支払額 |
| `settlement_amount` / `settlement_from_user_id` / `settlement_to_user_id` | 精算額と、誰が誰に払うか |
| `confirmed_by`・`confirmed_at` / `reopened_by`・`reopened_at` | 直近の確定・再オープンの操作 |

### 3.4 グループ・メンバー

| テーブル | 内容 |
|---|---|
| `groups` | グループ名、作成者 |
| `group_members` | `role`（admin／member）、`user_id`（招待中は NULL）、`invited_email`・`invited_display_name`。トリガーで1グループ2人までに制限する（`enforce_group_member_limit`） |
| `profiles` | 表示名・色（`blue`／`red`／未設定）・メールアドレス。ユーザー作成時にトリガーで作る |

### 3.5 分類

| テーブル | 内容 |
|---|---|
| `categories` | アプリ共通のカテゴリ（食費・日用品・衣類・ファッション・交通費・通信費・賃料・水道光熱費・娯楽・宿泊・旅行・医療費・学習・自己投資・その他・投資・保険料）。`default_cost_type` が費用区分の初期値。並び順は ID 順（「投資」「保険料」は Issue #49 で追加したため「その他」の後ろ） |
| `category_settings` | グループごとの費用区分。行がなければ `default_cost_type` を使う |
| `category_breakdowns` | グループ・カテゴリごとの内訳。名前・並び順・非表示・費用区分（`cost_type`。固定費・変動費のどちらかを必ず持つ。作るときに指定がなければ、トリガー `fill_breakdown_cost_type` でそのときのカテゴリの費用区分が入る。空は CHECK 制約で禁止。Issue #49） |
| `counterparts` | 相手。`kind` は `member`（メンバー。`user_id` を持ち、名前は表示名を使う）／`default`（ふたり・友人・実家）／`custom`（任意）。グループ作成・メンバー参加時にトリガーで作る。既定・メンバーの相手は名前の変更・削除をトリガーで禁止する |
| `tags` | グループのタグ。名前・並び順・非表示 |

### 3.6 支払い先

| テーブル | 内容 |
|---|---|
| `payees` | 名前（グループ内で一意）と**共通の既定値**（カテゴリ・内訳・相手・帰属先・商品名）。帰属先は `default_owner_joint`（共同）か `default_owner_user_id`（メンバー）。相手・帰属先の「登録する人」は `default_counterpart_registrant`・`default_owner_registrant` |
| `payee_default_tags` | 共通の既定値のタグ |
| `payee_member_defaults` / `payee_member_default_tags` | メンバーごとの**自分用の既定値**とそのタグ。行がある＝そのメンバーは自分用を使う |
| `payee_hidden_members` | 行がある＝そのメンバーは自分のプルダウンでその支払い先を非表示にしている |
| `payee_aliases` | 別名。支払い先の名前とも重複できない |

既定値の整合（内訳・相手・帰属先・タグが支払い先のグループのものか、共同とメンバーの両方を持たないか）はトリガー（`check_payee_defaults`・`check_payee_member_defaults`・`check_payee_default_tag`）で、名前と別名の重複は `check_payee_name_not_alias`・`check_payee_alias` で確かめる。メンバーがグループから外れたら、その人の自分用の既定値を削除する（`delete_payee_member_defaults_on_leave`）。

### 3.7 マスタ

| テーブル | 内容 |
|---|---|
| `transaction_types` | 支出・返金 |
| `consumption_taxes` | 税別のときの税率。8%（1.08）・10%（1.10） |

### 3.8 ストレージ

- バケット `receipt-images`（非公開）。パスは `{group_id}/{receipt_id}/{uuid}.{拡張子}`
- 先頭の `group_id` が自分のグループのときだけ、読み書き・削除できる（`storage.objects` のポリシー）
- 登録時は画像をアップロードしてから DB に保存し、DB の保存に失敗したら画像を削除する。画像の差し替え・レシートの削除では、古い画像を同時に削除する
- アップロード前に、ブラウザで画像を縮小する（`lib/receipts/resize-image.ts`）

### 3.9 主な関数（RPC）

| 関数 | 内容 |
|---|---|
| `my_group_ids()` / `is_group_admin(group_id)` / `shares_group_with(user_id)` | RLS で使う所属・権限の判定 |
| `create_group_with_admin` | グループを作り、作成者を管理者として登録する |
| `link_pending_group_memberships` | ログインしたユーザーを、事前登録されたグループに紐づける |
| `is_settlement_confirmed(group_id, occurred_at)` | その月が確定済みか。レシート・明細の書き込みのポリシーで使う |
| `confirm_settlement` / `reopen_settlement` | 精算の確定／再オープン（どちらも `is_group_admin` で管理者だけに限る） |
| `add_payee_alias` | 別名を追加し、店名が一致する過去のレシートを切り替える |
| `used_setting_ids` | レシートで使われている内訳・相手・タグ・支払い先の ID（設定画面の削除ボタンの非活性に使う） |
| `normalize_payee_name` | 店名の照合用に前後の空白を除く |

## 4. 権限

画面でボタンを隠すだけでなく、サーバーアクションと RLS の両方で確かめる。すべてのテーブルで、他グループのデータは参照・変更できない。

| データ | 参照 | 追加・変更・削除 |
|---|---|---|
| レシート・明細・明細のタグ・画像 | グループのメンバー | グループのメンバー。**精算確定済みの月は不可**（`is_settlement_confirmed`） |
| 精算の確定記録 | グループのメンバー | 確定・再オープンとも管理者（どちらも RPC 経由だけ。RPC の中で `is_group_admin` を確かめる） |
| カテゴリの費用区分・内訳 | グループのメンバー | 管理者 |
| 相手 | グループのメンバー | 管理者（既定・メンバーの相手は表示／非表示だけ） |
| タグ | グループのメンバー | グループのメンバー |
| 支払い先・共通の既定値・既定値のタグ | グループのメンバー | グループのメンバー |
| 別名 | グループのメンバー | 追加は `add_payee_alias` だけ、削除はグループのメンバー |
| 自分用の既定値・非表示 | グループのメンバー | 自分の分だけ |
| メンバー（招待・表示名・除籍） | グループのメンバー | 管理者（管理者自身は除籍できない） |
| プロフィール | 本人・同じグループのメンバー | 管理者（グループのメンバーの表示名・色） |
| カテゴリ・取引種別・税率 | ログインしているユーザー | なし（マスタ） |

## 5. 機能の設計

### 5.1 グループ・メンバー

- ログイン後、所属するグループがなければ `/setup/group` に誘導する（`lib/supabase/group.ts`）
- 管理者が Gmail アドレスで事前登録すると `group_members` に `user_id` が NULL の行ができる。その人が初めてログインしたとき、`/auth/callback` で `link_pending_group_memberships` を呼んで紐づける
- 実装：`lib/actions/create-group.ts`・`invite-group-member.ts`・`remove-group-member.ts`・`update-member-display-name.ts`・`update-invited-member-display-name.ts`・`update-member-color.ts`

### 5.2 レシートの登録・編集

実装：`components/receipt-form/`、`lib/actions/create-receipt.ts`・`update-receipt.ts`・`delete-receipt.ts`、検証は `lib/validation/receipt-rules.ts`、保存行の組み立ては `lib/receipts/shared.ts`

- 送信前に確認のモーダルを出す。明細の合計と支払額が一致するかは確かめない（金額の不一致の警告はコミット ae55daf で廃止した）
- 内訳は、内訳のあるカテゴリでは必須。カテゴリを変えたら選び直し（内訳が1つなら自動で選ぶ）。内訳のない既存の明細も、編集して保存するときは内訳を求める
- 画像の読み取り：`lib/actions/extract-receipt-ocr.ts` → `lib/gemini/extract-receipt.ts`。支払い先名・日時・支払額・明細（商品名・価格・推定税率）を返す。税率は推定値を初期値にするだけ
- 一括入力（`BulkInputModal`）：全明細のカテゴリ・内訳・相手・帰属先・タグ・特別費を同じ値にする。項目ごとに「変更しない」を選べる
- 複製登録（`lib/receipts/duplicate.ts`）：新規登録の2件目として、支払者＝相方・`is_duplicated = true` のレシートを登録する。帰属先は「私 → 相方」だけ置き換える。画像は別ファイルとしてコピーする。2件目の登録に失敗したら1件目と画像を削除する
- 確定済みの月への登録・編集・削除は、サーバーアクションでエラーを返し、RLS でも拒否する

### 5.3 支払い先

実装：`lib/receipts/payees.ts`（既定値の選択・適用・照合）、`lib/actions/settings/payees.ts`、`components/settings/PayeeSettingsManager.tsx`

- **プルダウン**：自分が非表示にしていない支払い先を名前順に出す。編集時に、自分が非表示にしている支払い先が選ばれていれば「〇〇（非表示）」として残し、そのまま保存できる
- **使う既定値**（`payeeDefaultsFor`）：自分用があれば自分用、なければ共通。共通の「登録する人」は、操作しているメンバー（相手はそのメンバーの「メンバーの相手」）に置き換える。本人のメンバーの相手が非表示なら、相手は空欄にする
- **既定値の適用**（`applyPayeeDefaults`）

  | 項目 | 入れ方 |
  |---|---|
  | カテゴリ・内訳・相手・帰属先・タグ | 全明細を上書きする。既定値がない項目は未選択にする。「該当なし」（手入力）・未選択も既定値なしとして扱う |
  | 商品名 | 商品名が空（空白だけを含む）の明細にだけ入れる |

  - 内訳は、内訳の既定値があればそれ、なければカテゴリの内訳が1つだけのとき自動で選ぶ
  - 既定値の内訳がカテゴリに属していない・非表示、相手が非表示、帰属先のメンバーがグループにいない、タグが非表示のときは、その既定値は使わない
  - タグは置き換え（追加ではない）
- **店名の照合**（`findPayeeByName`）：グループのすべての支払い先（自分が非表示にしているものを含む）の名前・別名と、前後の空白を除いた完全一致で照合する

  | 一致した支払い先 | 手入力 | 画像の読み取り |
  |---|---|---|
  | 自分が表示している | 保存時に支払い先だけを設定（入力欄の下に「保存時に『〇〇』として保存されます」と出す） | プルダウンで選び、既定値を入れる |
  | 自分が非表示にしている | 保存時に支払い先だけを設定 | 手入力欄に入れ、保存時に支払い先だけを設定 |
  | なし | 手入力のまま保存 | 同左 |

- **設定画面**：1つの一覧に、名前・既定値（共通か自分用か）・別名・自分の表示／非表示を出す。表示（表示中／非表示／すべて）と既定値（すべて／自分用／共通）で絞り込める（画面の中だけ。編集中の行は条件から外れても閉じるまで出す）。「自分用にする」で共通の値をコピーして編集でき、「共通に戻す」で自分用を削除する。相方が自分用を持つ行には「〇〇さんは自分用」と出す
- 制約：編集欄では、自分用と共通のどちらか一方しか編集できない。一覧の絞り込みの選択は保存しない

### 5.4 分類の設定

実装：`components/settings/`、`lib/actions/settings/`、取得は `lib/settings/queries.ts`

- **カテゴリ**：カテゴリごとに費用区分のプルダウンと内訳の一覧（追加・名前の変更・削除・非表示・費用区分）を出す。内訳の名前は同じカテゴリの中で重複できない（`lib/receipts/breakdowns.ts`）。内訳の費用区分は「固定費」「変動費」の2つから選び、そのまま保存する（`updateBreakdown` の `costType`）。カテゴリの費用区分と一致している方に「（カテゴリと同じ）」と添えるだけで、カテゴリの区分を変えても内訳の区分は変わらない
- **相手**：メンバー（表示名に連動）・既定（ふたり・友人・実家）・任意の相手を並べる。レシートの入力画面では、本人を「自分（A）」と表示する（保存する値は変わらない）（`lib/receipts/labels.ts`）
- **タグ**：追加・名前の変更・削除・非表示。今は集計に使わない（一覧・詳細で表示するだけ）
- **削除**：`used_setting_ids` でレシートに使われているものを調べ、削除ボタンを非活性にして理由を表示する。支払い先の既定値で使われている内訳・相手・タグは削除でき、外部キーで既定値が NULL（設定しない）に戻る

### 5.5 支出分析

実装：`lib/analytics/`（`queries.ts` 取得・按分、`aggregate.ts` 集計、`dimensions.ts` 項目、`months.ts` 月、`url-state.ts` 状態、`payees.ts` 支払い先の選択肢、`category-colors.ts` 色）、`components/analytics/`

- **取得**（`getAnalyticsData`）：当月を含む12か月のレシートと明細を、1,000件ずつページングして全件取得する（並び順は `occurred_at`・`id` で一意にし、ページ間の重複・漏れを防ぐ）。レシートごとに按分・返金の符号反転をして、「月 × カテゴリ × 内訳 × 相手 × 支払い先 × 帰属先 × 特別費」ごとに合計した行（`AnalyticsRow`）を画面に渡す。算出方法は [用語と算出方法.md](./用語と算出方法.md) 2〜3章
- **項目**（`dimensions.ts`）：分ける・絞り込みの項目は、カテゴリ・内訳・費用区分・支払い先・相手・特別費。値はすべて文字列で持つ（URL にそのまま載せるため）
  - 内訳のない明細は「内訳なし」にまとめる
  - 費用区分は集計するときの設定で、内訳の費用区分 → カテゴリの費用区分の順に決める（`costTypeOf`。明細には保存しない）
  - 支払い先は支払い先 ID で集計し、手入力は「登録外（手入力）」1つにまとめる。選択肢は名前順、最後に「登録外」。全員が非表示にしている支払い先は、12か月で使われているときだけ出す
- **投資を含める**（Issue #49）：カテゴリ「投資」は名前で見分ける（`investmentCategoryId`。カテゴリの ID は環境ごとに違うため）。OFF（初期値）のときは、条件に `excludeCategory`（投資のカテゴリ ID）を足して、集計・一覧へのリンクから除く（`analysisConditions` の4つ目の引数）。絞り込みで投資のカテゴリ・内訳を選んでいる間は含める（`isInvestmentForced`）。状態は URL の `investment=1`
- **画面**：「条件」の欄（表示対象・共同を含める・特別費を含める・投資を含める・絞り込み・分ける）は折りたたみ、閉じているときも条件の要約を出す
  - 円グラフ：選んだ月を「分ける」の値ごとに集計し、表に金額・割合を出す。表の行を押すと、同じ条件のレシート一覧に移る
  - 推移グラフ：12か月の棒（金額）と折れ線（前月比）。棒を選んで「この月のレシートを見る」で一覧に移る。当月は月の途中であること、左端の月は前月比がないことを注記する
  - 返金で値がマイナスのときは、描画は0にして注意書き（`NegativeAmountNotice`）を出す
  - 「直近12ヶ月の特別費」の合計（0円のときは出さない）を押すと、特別費の一覧に移る
- **色**：カテゴリはカテゴリごとの固定の色、それ以外の項目はパレットの色。メンバーの色は青・赤の2色だけにして、グラフの色と紛れないようにする

### 5.6 レシート一覧

実装：`lib/receipts/queries.ts`（月の一覧の取得）、`list-params.ts`（URL の条件）、`list-view.ts`（絞り込み）、`list-search.ts`（キーワード）、`lib/analytics/drilldown.ts`（分析の条件の当てはまりと「うち」金額）、`components/receipt-list/`

- 選んだ月のレシートを、明細・画像の URL まで含めて取得する。フィルタ・分析の絞り込みは、取得した一覧を画面の中で絞り込む
- **フィルタ**：ユーザー（支払者／負担者。負担者は共同の1/2を含めるかを選べる）・期間（月の中の日付）・キーワード（支払い先名・商品名）。条件は AND。月を切り替えると期間だけ外す
- **分析からの絞り込み**：URL で月・表示対象・絞り込み・分けた値・特別費を受け取る。分析画面から渡された表示対象は、フィルタ欄の「負担者」として表示し、変えられる
- **件数**：絞り込み中は条件と件数を出す。合計は出さない（Issue #49）。`buildReceiptListView` の `matchedTotal`（「うち」金額の合計）は、グラフの金額と一致することをテストで確かめるためだけに残している
- 分析画面から来た「投資を除く」は URL の `excludeCategory`（カテゴリ ID）で受け取る
- 開いた行では、条件に当てはまる明細を通常の表示、当てはまらない明細を薄く表示する。明細の金額は入力した価格のまま（按分後の金額との違いは許容する）

### 5.7 特別費の一覧

実装：`lib/analytics/special-expense-list.ts`、`app/(app)/analytics/special-expenses/page.tsx`

- 直近12か月の、特別費の明細を含むレシートだけを DB で絞り込んで取得し、月ごとに新しい順に並べる
- 金額は表示対象に合わせた按分後の特別費の金額で、合計は分析画面の「直近12ヶ月の特別費」と一致する
- 「← 分析に戻る」で元の分析画面へ戻る。レシート詳細の「戻る」はこの一覧に戻る

### 5.8 精算

実装：`lib/settlement/calculate.ts`（計算）、`lib/settlement/queries.ts`（取得）、`lib/actions/confirm-settlement.ts`・`reopen-settlement.ts`、`components/settlement/`

- 月を選ぶと、その月のレシートから都度計算して表示する。確定済みの月は、保存した結果を表示する。算出方法は [用語と算出方法.md](./用語と算出方法.md) 4章
- 確定・再オープンは確認のモーダルを挟む。どちらのボタンも管理者だけ押せる（一般メンバーには理由を表示する）
- 確定済みの月のレシートは、詳細画面の編集・削除ボタンを非活性にして理由を表示する

## 6. 既知の制約

| 内容 | 影響 |
|---|---|
| E2E テストは自動化していない（開発環境に Playwright のブラウザを入れられないため） | 画面操作は Issue ごとの受け入れテスト仕様書で手動確認する |
| 支払者・帰属先がグループのメンバーかは DB では確かめない | サーバーアクションの検証に頼る |
| 精算の確定の履歴は残さない | 再確定すると前回の結果は上書きされる |
| 費用区分は明細に保存しない | 区分を変えると過去の月の集計も変わる |
| 一覧の明細の金額は按分前の入力額 | 割引のあるレシートでは、一覧の明細の金額と「うち」金額が一致しない |
