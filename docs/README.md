# docs

このアプリの文書は、**全体仕様書**と **Issue ごとの仕様書**の2層で管理する（2026-11-26、Issue #47 で整理）。

```
docs/
├── README.md              この文書
├── 全体仕様書/              アプリ全体の「今の正しい仕様」
│   ├── 要件定義書.md
│   ├── 基本設計書.md
│   ├── 用語と算出方法.md
│   ├── 運用手順.md
│   └── 画面仕様書/          画面ごとに、利用者ができることと数字の求め方
│       ├── README.md       画面の一覧・ヘッダー・画面のつながり
│       └── NN_画面名.md
└── 仕様書/                 Issue ごとの仕様
    └── #<Issue番号>_<Issueのタイトル>/
        ├── 要件定義書.md
        ├── 詳細設計書.md
        └── 受け入れテスト仕様書.md
```

## 全体仕様書

| 文書 | 内容 |
|---|---|
| [要件定義書.md](./全体仕様書/要件定義書.md) | 目的・機能要件・非機能要件・対象外・変更履歴 |
| [基本設計書.md](./全体仕様書/基本設計書.md) | 技術構成・画面・DB・権限・機能ごとの設計・既知の制約 |
| [用語と算出方法.md](./全体仕様書/用語と算出方法.md) | 用語の定義と、分析・精算の数字の算出方法 |
| [運用手順.md](./全体仕様書/運用手順.md) | 開発環境・本番環境の設定・本番リリース・ローカルのテストデータ |
| [画面仕様書/](./全体仕様書/画面仕様書/README.md) | 画面ごとに、利用者ができること・表示される数字の求め方・誰ができるか（技術的な仕組みは書かない） |

- テストの項目（単体・結合・E2E・受け入れ）は全体仕様書に持たず、Issue ごとの仕様書に書く

## Issue ごとの仕様書

| 文書 | 内容 |
|---|---|
| `要件定義書.md` | Issue へのリンク・ブランチ・用語・背景・仕様・対象外・影響・完了基準。不具合修正では原因と修正方針も書く |
| `詳細設計書.md` | 方針・DB・型と関数・Server Action・画面・テスト項目（単体・結合・E2E）・既知の制約 |
| `受け入れテスト仕様書.md` | 画面で確認する手動テストの項目と結果 |

## 更新のルール

1. すべての作業は GitHub の Issue に起票してから始める。バグ報告も Issue の本文に書く（ラベル `bug`）
2. 要件が確定したら、`仕様書/#<番号>_<タイトル>/` を作り、要件定義書を書く
3. 実装と並行して、詳細設計書と受け入れテスト仕様書を書く
4. 完了時に、全体仕様書の該当箇所を更新する（要件定義書の「変更履歴」にも1行足す。画面が変わるときは画面仕様書も）
5. dev へのマージが終わったら、Issue の本文を最終版に書き直す
6. コードのコメントから文書を参照するときは、全体仕様書の文書と節（例：`docs/全体仕様書/基本設計書.md 5.5節`）か、Issue 番号（例：`Issue #41`）で書く

Issue #47 より前の文書（`requirements.md`・`basic-design.md`・`test-spec.md`・`支出分析機能/`・`分析拡充/` など）は全体仕様書に統合して削除した。内容は git の履歴（コミット 4cc0d65 まで）で参照できる。
