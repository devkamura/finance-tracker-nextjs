## 3. 本番のDBに反映する前（本番DBの確認）

本番のプロジェクトに `supabase link --project-ref <本番プロジェクトref>` した状態で行う。SQL は Supabase ダッシュボードの SQL Editor で実行する。

### 3.1 バックアップ

- [ ] 本番DBのバックアップを取る（`supabase db dump -f prod-schema.sql` と `supabase db dump --data-only -f prod-data.sql`）。ダッシュボードの「Database → Backups」に直近のバックアップがあるかも確認する
- [ ] バックアップのファイルはリポジトリにコミットしない（個人の家計データのため）

### 3.2 マイグレーションの状態

- [ ] `supabase migration list` で、本番に適用済みのマイグレーションが `20260927000001_receipt_is_duplicated.sql` までで、未適用が今回の分（1章）だけであることを確認する

### 3.3 データの書き換えの件数と記録

交際費の削除は元に戻せないため、移す前の明細を記録しておく。

- [ ] 交際費の明細の件数を確認し、明細IDの一覧を保存する

  ```sql
  select d.id, d.receipt_id, r.occurred_at, r.store_name, d.item_name, d.price
  from receipt_details d
  join categories c on c.id = d.category_id
  join receipts r on r.id = d.receipt_id
  where c.name = '交際費'
  order by r.occurred_at;
  ```

- [ ] カテゴリ「その他」が本番にあることを確認する（ない場合は交際費の移し先がなく、マイグレーションがエラーで止まる）

  ```sql
  select id, name from categories where name in ('交際費', 'その他');
  ```

- [ ] 色が「未設定」に戻るメンバーを確認し、反映後に管理者が選び直すことを伝えておく

  ```sql
  select id, color from profiles
  where color is not null and color not in ('blue', 'red');
  ```

- [ ] 反映前の精算の結果を控える（直近2〜3か月分の画面のスクリーンショット）。反映後に同じ値になっているかを比べる

## 4. 反映の手順と順番

**DB を先に、アプリを後に反映する。** 新しいアプリは `category_breakdowns` などの新しいテーブルを読むため、DB が古いままだと画面がエラーになる。逆に、古いアプリ＋新しい DB でも短時間なら動く（メンバーの色で青・赤以外を選ぶと保存できない程度）。

- [ ] 本番DBに反映する：`supabase db push --include-seed`
- [ ] `supabase migration list` で今回の分が適用済みになっていることを確認する
- [ ] dev を main にマージする（GitHub で PR）→ Vercel のデプロイが成功したことを「Deployments」で確認する
- [ ] Vercel の環境変数は変更不要であることを確認する（1章のとおり追加の環境変数はない）

- [ ] Google でログイン・ログアウトできる
- [ ] レシートの登録・編集・複製登録・一括入力ができる（内訳があるカテゴリでは内訳を選べる）
- [ ] 交際費がカテゴリの選択肢に出ない。3.3 で記録した明細が「その他」になっている

- [ ] 分析画面（円グラフ・推移グラフ・一覧への絞り込み）が表示され、一覧の合計と一致する

- [ ] Vercel の「Logs」にエラーが出ていない

## 6. 問題が起きたときの戻し方

- アプリ：Vercel の「Deployments」で1つ前のデプロイを「Promote to Production」（Instant Rollback）で戻す。ただし DB は新しいままなので、メンバーの色は青・赤しか保存できない。
- DB：マイグレーションは自動では戻らない。
  - 新しいテーブル・列は、使わなければ古いアプリの動作に影響しない。基本はアプリだけ戻して、DB は残したまま直す。
  - 交際費を戻す必要がある場合は、カテゴリ「交際費」を作り直し、3.3 で記録した明細IDのカテゴリを交際費に戻す。
  - それでも直らない場合は 3.1 のバックアップから復元する（反映後に登録されたデータは失われるので、最後の手段にする）。
