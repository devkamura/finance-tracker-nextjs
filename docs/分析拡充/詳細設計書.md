## F1：設定画面の土台＋カテゴリの内訳・費用区分

ブランチ：`feature-i0008-category-breakdown`（`feature-detailed-analysis` から作成）
ステータス：**画面確認済み**（2026-10-03）

### 1. 対象範囲

| 区分 | 内容 |
|---|---|
| DB | カテゴリの費用区分の初期値、グループごとの費用区分（`category_settings`）、内訳（`category_breakdowns`）、明細の内訳（`receipt_details.breakdown_id`） |
| 設定画面 | `/settings` を新設（ヘッダーの「設定」は `/settings/categories` へ。`/settings` は `next.config.ts` の `redirects` でカテゴリへ転送）。F1 ではカテゴリのタブのみ（費用区分と内訳の追加・名前の変更・表示/非表示・削除） |
| 登録・編集画面 | 内訳の欄（必須・自動選択・非表示の既存値の表示）、一括入力の内訳 |
| 一覧・詳細 | 「食費 ＞ 外食」の表示 |

カテゴリ「交際費」の削除も F1 で行う（`20261003000003_delete_social_category.sql`）。既存の交際費の明細はカテゴリを「その他」にし、内訳は外す。相手は設定しない（基本設計書 Q7：ユーザー確認済み）。

### 2. DB（`supabase/migrations/20261003000002_category_breakdowns.sql`）

| 対象 | 内容 |
|---|---|
| `categories.default_cost_type` | 費用区分の初期値（`fixed`／`variable`）。賃料・水道光熱費・通信費は `fixed`、それ以外は `variable`（基本設計書 Q5） |
| `category_settings` | グループ×カテゴリの費用区分。行がなければ `default_cost_type` を使う |
| `category_breakdowns` | グループ×カテゴリの内訳。名前はカテゴリ内で一意。`is_hidden`（非表示）、`sort_order`（末尾に追加） |
| `receipt_details.breakdown_id` | 明細の内訳（任意）。`on delete restrict`（使われている内訳は削除できない。基本設計書 Q4） |
| トリガー `check_receipt_detail_breakdown` | 明細の内訳が、明細のカテゴリ・レシートのグループの内訳であることを保証する |
| RLS | 参照はグループのメンバー全員、書き込みは管理者のみ（`is_group_admin`。基本設計書 Q2） |

### 3. 共通処理

| ファイル | 内容 |
|---|---|
| `lib/receipts/breakdowns.ts` | 型（`CategoryBreakdown`・`CostType`）、表示中の内訳、内訳が必須か、自動で選ぶ内訳、内訳がカテゴリのものか（画面・入力チェック共通） |
| `lib/settings/queries.ts` | 内訳の取得、カテゴリと費用区分の取得（グループの設定 → 初期値の順） |
| `lib/settings/admin.ts` | 設定の Server Action で使う、管理者の確認 |
| `lib/actions/settings/*.ts` | 内訳の追加・変更（名前・表示/非表示）・削除、費用区分の変更 |

### 4. 登録・編集画面

- `ReceiptItem.breakdownId`、`MasterData.breakdowns`（非表示を含む）を追加。
- 内訳の欄は、カテゴリに表示中の内訳がある（または非表示の内訳が選ばれている）ときだけ表示する。非表示の内訳は「（非表示）」付きで、選ばれている場合だけ選択肢に残す。
- カテゴリを変えたら内訳を選び直し、表示中の内訳が1つだけなら自動で選ぶ（`ReceiptForm` の `withBreakdownForCategory`）。一括入力も同じ。
- 一括入力：カテゴリを選ぶと内訳の選択肢が出る（「各項目で選ぶ」＝各項目で選び直し）。
- 入力チェック（`validateReceiptForm` の第3引数に内訳）：表示中の内訳があるカテゴリでは必須、選んだ内訳はそのカテゴリのもの（非表示の既存値は可）。Server Action（登録・更新）でも同じチェックを行う。既存の内訳なしのレシートも、編集して保存するときは内訳が必要（基本設計書 Q8）。
- 複製登録は明細をそのままコピーするため、内訳も引き継がれる。

## F2：相手・タグ

ブランチ：`feature-i0009-counterpart-tag`（`feature-detailed-analysis` から作成）
ステータス：**実装済み・画面確認待ち**（2026-10-03）

### 1. 対象範囲

| 区分 | 内容 |
|---|---|
| DB | 相手（`counterparts`）・タグ（`tags`・`receipt_detail_tags`）の新設、明細の相手（`receipt_details.counterpart_id`）、目的・シーンからの移し替え、目的・シーンの削除 |
| 設定画面 | 「相手」「タグ」のタブを追加（`/settings/counterparts`・`/settings/tags`） |
| 登録・編集画面 | 目的 → 相手（「自分（A）」の表示）、シーン → タグ。一括入力の目的 → 相手 |
| 一覧・詳細 | 「目的」→「相手」、「シーン」→「タグ」のバッジ |

### 2. DB（`supabase/migrations/20261003000004_counterparts_tags.sql`）

| 対象 | 内容 |
|---|---|
| `counterparts` | グループの相手。`kind`：`member`（メンバー。`user_id` を持ち、名前は持たない）／`default`（ふたり・友人・実家）／`custom`（任意）。`is_hidden`、`sort_order`（メンバー 0、既定 1〜3、任意は末尾） |
| 一意性 | メンバーはグループ×ユーザーで1つ。既定・任意の名前はグループ内で重複できない |
| トリガー `protect_builtin_counterparts` | メンバー・既定の相手は名前・種類・ユーザーを変えられない（表示・非表示と並び順のみ） |
| トリガー（自動作成） | グループ作成時に既定の相手（`groups` の after insert）、メンバー参加時にメンバーの相手（`group_members` の after insert / update of user_id。招待中は作らず、参加して `user_id` が入った時点で作る） |
| `receipt_details.counterpart_id` | 明細の相手（必須。基本設計書 Q3）。`on delete restrict`（使われている相手は削除できない。Q4） |
| トリガー `check_receipt_detail_counterpart` | 明細の相手が、レシートのグループの相手であることを保証する |
| `tags` | グループのタグ。名前はグループ内で一意。`is_hidden`、`sort_order` |
| `receipt_detail_tags` | 明細×タグ。`tag_id` は `on delete restrict`。トリガー `check_receipt_detail_tag` でグループの一致を保証する |
| RLS | 参照はグループのメンバー全員。相手は管理者のみ編集でき、追加・削除できるのは `custom` だけ。タグはグループのメンバー全員が編集できる（集計に使わないため。Q2：ユーザー確認済み） |

**移し替え（基本設計書 5章・Q7 の案のとおり）**

| 目的 | 相手 |
|---|---|
| 生活維持 | ふたり |
| 個人 | 明細の帰属先のメンバー（共同のときは ふたり） |
| 仕事 | 個人と同じ（明細の帰属先のメンバー。共同のときは ふたり）。相手「仕事」は作らない（ユーザー確認済み） |
| 家族 | 実家 |
| 友人 | 友人 |
| 上記以外 | 同じ名前の任意の相手 |

- シーン → タグ：今のシーンをすべて同じ名前のタグとして各グループに作り（並び順はシーンの順）、明細のシーンをタグに移す。
- 移し替えのあと、`receipt_details.purpose_id`・`receipt_detail_scenes`・`scenes`・`purposes` を削除する（古いアプリは動かなくなる。本番デプロイ前チェックリスト参照）。
- 新しく作るグループには、タグは作らない（設定画面で追加する）。

### 3. 共通処理

| ファイル | 内容 |
|---|---|
| `lib/receipts/labels.ts` | 型（`Counterpart`・`Tag`）、プルダウンの表示（「自分（A）」「（非表示）」）、選択肢（表示中＋選ばれている非表示）、グループの相手・タグかの判定 |
| `lib/settings/queries.ts` | `getCounterparts`（メンバーの名前は表示名。グループから外れたメンバーの相手は含めない）、`getTags` |
| `lib/actions/settings/counterparts.ts` | 任意の相手の追加・名前の変更・削除、表示・非表示（メンバー・既定も可） |
| `lib/actions/settings/tags.ts` | タグの追加・名前の変更・表示/非表示・削除（メンバー全員。`requireGroupMember` でログイン・グループ所属だけを確認する） |
| `components/settings/NamedItemListManager.tsx` | 相手・タグの設定画面の共通の一覧（追加・名前の変更・表示/非表示・削除） |

### 4. 登録・編集画面

- `ReceiptItem.purposeId`・`sceneIds` → `counterpartId`・`tagIds`。`MasterData.counterparts`・`tags`（非表示を含む）。
- 相手のプルダウン：表示中の相手（＋編集時に選ばれている非表示の相手）。ログイン中のユーザー自身は「自分（A）」と表示する（編集画面にも `currentUserId` を渡す）。
- タグ：表示中のタグ（＋選ばれている非表示のタグ）をボタンで複数選択。タグが1つもないときは欄を出さない。
- 入力チェック（`validateReceiptForm` の第4引数に相手・タグ）：相手は必須、相手・タグはグループのもの（非表示の既存値は可）。Server Action（登録・更新）でも同じチェックを行う。
- 複製登録：相手・タグは元の明細のまま（帰属先だけを置き換える既存のルールは変えない）。

#### 移し替えの確認

ローカルのデータ（明細15件：生活維持14件・友人1件、シーン1件）で、生活維持 → ふたり（14件）、友人 → 友人（1件）、シーン「夕食」→ タグ「夕食」になることを確認した。本番に反映する前に、本番のデータの件数で同じ確認を行う（本番デプロイ前チェックリスト 3.3）。

本番のバックアップ（2026-10-03 取得）をローカルに入れて、F1・F2 のマイグレーションを流すリハーサルを行い、エラーなく適用できた。

| 移し替え前 | 件数 | 移し替え後 | 件数 |
|---|---|---|---|
| 生活維持（共同 396・メンバー 9） | 405 | ふたり | 405 |
| 個人 89・仕事 2（すべて帰属先がメンバー） | 91 | 帰属先のメンバー（管理者 51・一般 40。帰属先と相手のずれ 0 件） | 91 |
| 友人 | 15 | 友人 | 15 |
| 家族 | 7 | 実家 | 7 |
| シーン（9種類に付いていた分） | 120 | 同じ名前のタグ | 120 |

明細の件数（518）と金額の合計は移し替えの前後で同じ。F3・F4 のマイグレーションを加えたら、dev → main の前に同じリハーサルをやり直す。
