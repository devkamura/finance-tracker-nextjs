### 3. 月の計算（`lib/analytics/months.ts`）

月・日は JST で判定する（基本設計書3.3節）。サーバーは `instrumentation.ts` で起動時に `TZ=Asia/Tokyo` に固定されているため、既存のレシート一覧・精算（`lib/receipts/queries.ts` の `monthPeriod`）と同じく、`getFullYear()`・`getMonth()`・`getDate()` で JST の値が得られる。既存と同じ書き方にそろえることで、同じレシートが一覧・精算と分析で別の月に入ることを防ぐ。

日付の計算はすべてサーバー側で行い、ブラウザには `"YYYY-MM"`・`"YYYY-MM-DD"` の文字列だけを渡す（ブラウザの時計・タイムゾーンには依存しない）。

| 関数 | 内容 | 例 |
|---|---|---|
| `todayKey(now: Date)` | 今日を `"YYYY-MM-DD"` で返す | `"2026-10-03"` |
| `monthKeyOf(date: Date)` | その時刻が属する月を `"YYYY-MM"` で返す | `"2026-09"` |
| `lastTwelveMonths(today)` | 当月を含む12か月を古い順に返す | `"2026-10-03"` → `["2025-11", …, "2026-10"]` |
| `monthRange(months)` | 12か月の取得範囲 [最初の月の1日0時, 最後の月の翌月1日0時) を返す | `["2025-11"…"2026-10"]` → [2025-11-01, 2026-11-01) |
| `addMonths(monthKey, n)` | 月キーをずらす | `("2026-01", -1)` → `"2025-12"` |

### 4. データ取得（`lib/analytics/queries.ts`）

#### 4.1 取得

```text
getAnalyticsData(supabase, groupId, now = new Date())
  today      = todayKey(now)
  months     = lastTwelveMonths(today)
  [from, to) = monthRange(months)
  receipts を occurred_at ∈ [from, to) で取得
    select: id, occurred_at, amount, payer_user_id, transaction_types(name),
            receipt_details(price, tax_type, category_id, owner_user_id, consumption_taxes(multiplier))
    order:  occurred_at, id
    1,000件ずつ range() で取得し、1,000件未満が返ったら終了
  members    = getGroupMembers()（既存）
  categories = categories を id 順に取得
```

- `supabase/config.toml` の `max_rows = 1000` はレシート（親）の件数に効く。明細（子）は各レシートにまとめて付いてくる。
- 取得エラー時は例外を投げる（既存ページと同じく Next.js のエラー画面に任せる）。

#### 4.2 変換と集約

1. レシートごとに、精算と同じ `allocateReceiptAmount` で支払額を明細に按分する（税込換算・最大剰余法を含む）。
2. 取引種別が「返金」なら、按分結果をマイナスにする。
3. 明細を **「月 × カテゴリ × 帰属先」ごとに合計して** 画面に渡す（確認事項1）。

```ts
// lib/analytics/types.ts
type AnalyticsRow = {
  month: string;              // "2026-09"
  categoryId: number;
  ownerUserId: string | null; // null＝共同
  amount: number;             // 按分・符号反転済みの合計（円、整数）
};

type AnalyticsData = {
  today: string;              // "2026-10-03"
  months: string[];           // 12か月（古い順）
  categories: { id: number; name: string }[];
  members: { userId: string; displayName: string; color: string | null }[];
  rows: AnalyticsRow[];
};
```

### 5. 集計ロジック（`lib/analytics/aggregate.ts`）

#### 5.1 表示対象

```ts
type Scope = { kind: "all" } | { kind: "user"; userId: string; includeJoint: boolean };
```

| 表示対象 | 対象の行 | 重み |
|---|---|---|
| 全体 | すべて | 1 |
| ユーザー（共同トグルオフ） | `ownerUserId === userId` | 1 |
| ユーザー（共同トグルオン） | 上記＋`ownerUserId === null` | 共同は 0.5 |

#### 5.2 カテゴリ別集計と端数

- `sumByCategory(rows, scope, month)`：カテゴリごとに合計する。
- 共同の1/2で出る0.5円は**丸めずにそのまま扱う**（確認事項2）。端数は .5 だけで、整数を2で割った値の和なので浮動小数点の誤差は出ない。
- 「A＋B＝全体」「内訳の合計＝表示する合計」が常に成り立つ。
- 表示：小数があるときは小数第1位まで（`8,500.5円`）、整数のときは小数なし（`5,200円`）。
- .5 が出るのはユーザー別表示で共同トグルがオンのときだけ。予算進捗（フェーズ5）は予算が全体のみのため .5 は出ない。ユーザー別予算を追加するときは、.5 と予算の比較方法を改めて検討する。

#### 5.3 円グラフ用データ

`buildPieData(categorySums)` は次を返す。

| 項目 | 内容 |
|---|---|
| `slices` | 金額がプラスのカテゴリ（金額の大きい順）。各カテゴリの `percent` は `amount ÷ positiveTotal × 100` を小数第1位で四捨五入 |
| `negatives` | 金額がマイナスのカテゴリ（注意書き用） |
| `zeroCategories` | 対象の行はあるが合計が0円のカテゴリ（表には出す） |
| `total` | 実際の合計（マイナスも含む） |
| `positiveTotal` | ％の分母（プラスのカテゴリの合計） |

- 明細が1件もない月：`slices` は空、`total` は0。画面には「この月の支出はありません」と表示する。
- プラスのカテゴリがない（すべて返金など）月：円グラフは描かず、表と注意書きだけを出す。

### 6. 画面（`/analytics`）

#### 6.1 構成

```text
分析
[全体|A|B]  □共同を含める        ← Bを選ぶと「□共同を含める」が出る
◀ 2026年9月 ▼ ▶                  ← 月の選択（過去12か月）
┌──────────────────────┐
│       （円グラフ）         │
│     合計 30,000円          │
└──────────────────────┘
⚠ 返金が支出を上回ったカテゴリは、グラフ上0として表示しています（衣類・ファッション −8,000円）。
  割合は、マイナスのカテゴリを除いた合計（38,000円）に対する値です。実際の合計は30,000円です。
┌──────────────────────┐
│ ● 食費        74.0%  28,000円 │
│ ● 日用品      26.0%  10,000円 │
│   衣類・ファッション  ―  −8,000円 │
└──────────────────────┘
```

- 表示対象のボタンは、メンバーの表示名（`UserBadge` と同じ色）で出す。メンバーが1人のグループでは「全体」と本人だけになる。
- 共同トグルはユーザーを選んだときだけ表示する。初期値はオフ。全体に戻すとトグルは隠れる（値はオフに戻す）。
- 月の選択は既存の `MonthSelector` と同じ見た目（◀ ▼ ▶）にする。ただし `MonthSelector` は URL 遷移（サーバー通信）を行うため使わず、画面内の状態だけを変える専用部品を作る。初期値は当月。
- 円グラフの扇はカテゴリの色で塗り、凡例の代わりに下の内訳表を使う。扇にマウスを乗せる（タップする）とカテゴリ名・金額・％を出す。選ばれた扇は半径を少し大きくして外に飛び出して見せる。ブラウザ標準のフォーカス枠は図形の外接矩形で描かれ、大きな扇では円全体を囲ってしまうため出さない（画面確認での指摘により追加）。
- 金額表記は既存画面に合わせて `toLocaleString()` ＋「円」。マイナスは `−8,000円`。

#### 6.2 状態と URL

- 状態：`scope`（全体 または ユーザーID）、`joint`（共同トグル）、`month`（"YYYY-MM"）。
- 初期状態はサーバー側で `searchParams` から読み、Client Component に props で渡す。不正な値は初期値（全体・オフ・当月）に戻す。
- 操作のたびに `window.history.replaceState` で URL を書き換える（例：`/analytics?scope=<userId>&joint=1&month=2026-09`）。Next.js のドキュメント上、`replaceState` はルーターと連携し、ページの再取得は起きない。
- `pushState` ではなく `replaceState` にする理由：操作ごとに履歴が増えると、ブラウザの「戻る」で切り替え操作を1つずつ巻き戻すことになるため（確認事項3）。この URL はフェーズ3で、レシート一覧から戻ったときの状態復元に使う。

#### 6.3 カテゴリの色（`lib/analytics/category-colors.ts`）

カテゴリ ID 順に12色の固定パレットを割り当て、13番目以降は先頭から繰り返す（色の重複は許容）。同じカテゴリは月や表示対象を変えても常に同じ色になる（確認事項4）。

メンバーの色（ブルー／レッド、6.5節）・共同の色（濃いグレー）と紛れないよう、青系・赤系・グレーを除いた12色にする。

### 3. 集計ロジック（`lib/analytics/aggregate.ts`）

#### 3.1 `sumByMonth(rows, scope, months, categoryId)`

- 12か月それぞれについて、表示対象（フェーズ1と同じ重み。共同オンなら共同は1/2）で合計する。
- `categoryId` が `null` のときは総支出（全カテゴリ）、数値のときはそのカテゴリだけ。
- データのない月は0円とする。返り値は `[{ month, amount }]`（古い順、12件）。

#### 3.2 `buildTrendData(series)`

各月について次を返す。

| 項目 | 内容 |
|---|---|
| `month` | `"2026-09"` |
| `amount` | 実際の金額（マイナスや0.5円もそのまま） |
| `barValue` | 棒の高さ。`amount` がマイナスなら0（基本設計書3.7節） |
| `mom` | 前月比（％、小数第1位で四捨五入）。`amount ÷ 前月のamount × 100`。最初の月、前月が0円以下、当月がマイナスのときは `null`（マイナスが絡む月は％の意味が読み取れないため。決算の前年比で「―」とする慣習と同じ） |

- 前月比は実際の金額で計算する。ただしマイナスが絡む月（前月が0円以下、または当月がマイナス）は算出しない（確認事項5）。当月が0円で前月がプラスなら0.0%。
- あわせて、金額がマイナスの月の一覧（注意書き用）を返す。

例（全体、テストデータ投入済みのローカル環境）

| 月 | 金額 | 棒 | 前月比 | 理由 |
|---|---|---|---|---|
| 2026-04 | 0円 | 0 | ― | 前月が0円 |
| 2026-05 | −3,000円 | 0 | ― | 前月が0円（当月もマイナス） |
| 2026-06 | 30,000円 | 30,000 | ― | 前月が0円以下（−3,000円） |
| 2026-07 | 5,001円 | 5,001 | 16.7% | 5,001 ÷ 30,000 × 100 |
| 2026-08 | 0円 | 0 | 0.0% | 0 ÷ 5,001 × 100 |

#### 4.1 構成

```text

┌───────────────────────────────┐

│ ▇                          ●───── 100 ┄┄ 基準線
│ ▇   ▇         ▇    ▇   ●          │
```

| 表示 | 条件 | 文言 |
|---|---|---|
| 当月の注記 | 「※注意事項」を開いたとき | 「※ 2026年10月は月の途中の金額です。前月比も途中までの金額で計算しています。」 |

| 注意書き（必須） | マイナスの月が1つ以上あるとき（折りたたまずに常に表示） | 「返金が支出を上回った月は、グラフ上0として表示しています（2026年5月 −3,000円、…）。」 |

## フェーズ3：グラフからレシート一覧への絞り込み

ブランチ：`feature-i0004-receipt-filter`
ステータス：**完了**（2026-10-03。手動確認はローカルで可能な項目をすべて実施済み）

### 1. 対象範囲

| 区分 | 内容 |
|---|---|
| 分析画面 | 円グラフの内訳表の行、推移グラフで選んだ月の「この月のレシートを見る」から、絞り込んだレシート一覧へ移動する |
| レシート一覧（既存を変更） | カテゴリ・表示対象での絞り込み、絞り込み中の表示と解除、上部の該当合計、各行の「うち〇〇 〇〇円」、該当する明細の強調 |
| 戻る | ブラウザの「戻る」で、タップしたときの状態（表示対象・グラフ種類・月・カテゴリ）の分析画面に戻る |
| レシート詳細・編集（既存を変更） | 絞り込み一覧から開いた場合、「一覧に戻る」で絞り込み一覧に戻る |

予算進捗画面からの絞り込み（フェーズ5）も、ここで作る仕組みを使う。

レシート一覧で利用者が自分で条件を選ぶフィルタ（カテゴリ・表示対象の選択欄など）は**付けない（保留）**。絞り込みは分析画面から移ってきたときだけ有効で、一覧でできるのは「解除」のみ。自由な条件での絞り込みは、要件定義書32〜33章（任意フィルタによる集計）の機能追加でまとめて設計する（2026-10-03 合意）。

### 2. 絞り込みの URL

既存の `month`・`sort`・`open` に、次のパラメータを追加する。どれもないときは、今までどおりの一覧になる。

| パラメータ | 値 | 意味 |
|---|---|---|
| `category` | カテゴリID | このカテゴリの明細を含むレシートに絞る。ないときは全カテゴリ（総支出） |
| `scope` | `all`／ユーザーID | 表示対象。ユーザーのときは帰属先がそのユーザーの明細に絞る |
| `joint` | `1` | 共同トグルオン。帰属先が共同の明細も含め、1/2で数える |
| `from` | `analytics` | 分析画面から来たことを表す。「← 分析に戻る」の表示に使う |
| `ret` | 分析画面の状態のクエリ文字列 | 「← 分析に戻る」で開く分析画面の状態。詳細・編集との行き来でも引き継ぐ |

例：`/receipts?month=2026-09&category=1&scope=all&from=analytics`

- 絞り込みが有効になるのは、`category`・`scope`（ユーザーID）のどちらかがあるとき、または `from` があるとき。
- 不正な値（存在しないカテゴリ・グループ外のユーザー）は無視する（その条件では絞らない）。

### 3. 分析画面からの移動

**グラフのタップは「見るだけ」、一覧への移動はリンクから**に統一する（確認事項4）。グラフをタップすると金額のツールチップが出るため、タップに移動を割り当てると、スマホで金額を見ようとしただけで別の画面に移ってしまうため。

| 画面 | 操作 | 動き |
|---|---|---|
| 円グラフ | 扇をタップ | ツールチップ（カテゴリ名・金額・％）を出すだけ。移動しない |
| 円グラフ | 内訳表の行をタップ | 選択中の月 × その行のカテゴリ × 表示対象・共同トグルで絞り込んだ一覧へ移動。マイナス・0円のカテゴリ（扇がない）もたどれる |
| 推移グラフ | 棒をタップ | その月を「選択中」にする（棒の色を濃くする）。グラフの下に「2026年7月　5,001円　前月比 16.7%」と「この月のレシートを見る →」を表示する |
| 推移グラフ | 「この月のレシートを見る →」 | 選択中の月 × 選択中のカテゴリ（総支出なら `category` なし） × 表示対象・共同トグルで絞り込んだ一覧へ移動 |

```text
（推移グラフ）
┌──────────────────────────┐
│ 2026年7月   5,001円   前月比 16.7%  │
│ この月のレシートを見る →             │
└──────────────────────────┘
```

- 推移グラフの選択中の月は、初期状態では選ばれていない（下の欄は「棒をタップすると、その月のレシートを見られます」と案内する）。選択中の月も URL（`trendMonth`）に保持し、戻ったときに復元する。
- 移動は `router.push` で行う。移動の直前の時点で、分析画面の状態はすでに `replaceState` で URL に入っている。
- 内訳表の行は、タップできることがわかる見た目（右端に「›」、押したときの背景色）にする。
- 一覧へのリンク（内訳表の行・「この月のレシートを見る」）は先読みしない（`prefetch={false}`）。Next.js の `<Link>` は本番環境では画面に表示された時点で移動先を先読みするため、そのままだと月や表示対象を切り替えるたびにサーバー通信が発生し、「画面を開いた後の操作では通信しない」要件に反する。開発環境では先読みが無効なため、手動テストでは検出できない点に注意。なお、このアプリのページはすべて動的なページで `loading.js` もないため、標準の先読みでも取得できるのは共通の枠（レイアウト）までで、一覧のデータは先読みされない。止めても表示の速さへの影響はわずか。分析画面から一覧へ移るとき（タップ時）のサーバーアクセスは許容する（2026-10-03 合意）。

### 4. 「戻る」で分析画面の状態を戻す

Next.js のドキュメント（用語集「Client Cache」）では、ブラウザの戻る・進むのときはページの描画結果をキャッシュから再利用する（サーバーへ取り直しに行かない）とされている。そのため、戻ったときに1年分のデータは取り直さない。

一方、画面の部品（Client Component）は作り直されるため、状態はサーバーから渡された初期値（最初に開いたときの URL の値）に戻ってしまう。これを防ぐため、`AnalyticsView` は**初期状態を現在の URL（`useSearchParams`）から読む**ように変える。URL の値が不正なときは、これまでどおりサーバーから渡された初期値を使う。

### 5. レシート一覧の絞り込み

#### 5.1 データ

- 既存の `listReceipts` の取得項目に、明細の `category_id` と税率の倍率（`consumption_taxes(multiplier)`）を追加する。`ReceiptDetailItemView` に `categoryId`・`taxRateMultiplier` を追加する（既存の表示は変えない）。
- **その月のレシートはサーバーから1回だけ取得し、絞り込み・解除・並び替えは画面側だけで行う**（サーバー通信なし。確認事項5）。月の切り替えだけは別の月のデータが必要なため、サーバーから取得する。
- 画面側の処理は純粋関数 `buildReceiptListView`（`lib/receipts/list-view.ts`）にまとめる。将来の任意フィルタ（要件定義書32〜33章）もここに条件を足して対応する。
- 状態（並び順・絞り込み）は分析画面と同じく、初期値を現在の URL から読み、変更は `replaceState` で URL に反映する（履歴に積まない）。
- ヘッダーの「一覧」など同じページへの移動で部品が使い回されると、画面側の絞り込みが残ってしまうため、サーバーが受け取った URL の条件が変わったときは部品を作り直す（`key` に一覧の URL パラメータを使う）。

#### 5.2 該当判定と「うち」の金額（`lib/analytics/drilldown.ts`、純粋関数）

`matchReceipt(receipt, filter)` は、レシート1枚について次を返す。

| 項目 | 内容 |
|---|---|
| `matchedItemIds` | 条件に当てはまる明細のID（カテゴリが一致し、かつ帰属先が表示対象に当てはまる） |
| `matchedAmount` | 当てはまる明細の按分後の金額の合計。共同トグルオンの共同の明細は1/2、返金はマイナス |

- 按分は分析と同じ `allocateReceiptAmount` を使う。そのため、一覧の上部に出す合計（全レシートの `matchedAmount` の合計）は、グラフの値と必ず一致する。
- 当てはまる明細が1件もないレシートは一覧に出さない。

#### 5.3 画面

```text
← 分析に戻る
レシート一覧
◀ 2026年9月 ▼ ▶
┌──────────────────────────────┐
│ 食費 ／ 全体 で絞り込み中        [解除] │
│ 食費の合計：2,500円                    │
└──────────────────────────────┘
09/14  スーパー     3,000円   うち食費 2,000円
09/20  コンビニ       500円   うち食費   500円
```

- 絞り込み中の表示：カテゴリ名（なければ「総支出」）と表示対象（「全体」「A」「A＋共同1/2」）。
- 合計の表示：「食費の合計：〇〇円」（カテゴリがなければ「該当の合計」）。返金が上回った場合はマイナスで表示する。
- 各行：これまでどおり支払額を表示し、その下に「うち食費 2,000円」（カテゴリがなければ「うち該当分」）を添える。0.5円は小数第1位まで表示する（分析と同じ `formatYen`）。
- アコーディオンを開いたとき：当てはまる明細は通常の表示、当てはまらない明細は薄く表示する。明細の金額は入力額のまま（按分後の金額との違いは許容済み、基本設計書2.5節）。
- 「解除」：画面側だけで絞り込みを外す（通信なし、履歴に積まない）。同じ月・並び順のまま通常の一覧になる。解除しても「← 分析に戻る」は表示したままにする（移動元 `from` は残す）。解除してからブラウザの「戻る」を押すと、分析画面に戻る。
- 「← 分析に戻る」：`from=analytics` のときだけ表示する。アプリ共通の「戻る」ボタン（`BackLink`、5.5節）を使う（確認事項9・10）。
  - 分析画面から直接来たときは1つ前に戻る（通信なし、分析画面は状態を URL から復元）。
  - 直前が分析画面でないとき（一覧 → 詳細 → 一覧をリンクで開き直した場合、月を切り替えた後など）は、タップしたときの状態の分析画面をリンクとして開く（通信あり）。そのため、分析画面から一覧へ移るとき、そのときの分析画面の状態（`serializeAnalyticsState` の結果）を一覧の URL の `ret` に入れ、詳細・編集との行き来でも引き継ぐ。
  - オープンリダイレクト対策：`ret` の値を行き先にはせず、行き先は常に `/analytics` に固定する。`ret` からは分析画面の状態の項目（scope・joint・month・chart・category・trendMonth）だけを取り出し、値の妥当性は分析画面側で検証する（`buildAnalyticsReturnHref`）。
- 並び順の切り替え：画面側だけで並べ替える（通信なし、履歴に積まない）。
- 月の切り替え・並び順の切り替えをしても、絞り込みは保つ（確認事項2）。
- 該当するレシートがないとき：「この条件に当てはまるレシートはありません。」

#### 5.4 詳細・編集との行き来

一覧 → 詳細 → 編集 → 詳細 → 一覧 と移動しても絞り込みが保たれるよう、一覧の URL パラメータ（`month`・`sort`・`category`・`scope`・`joint`・`from`）をまとめて引き継ぐ（確認事項3）。引き継ぎは小さな共通関数（`lib/receipts/list-params.ts`）にまとめ、詳細・編集・削除の戻り先で使う。

- 詳細画面の「← レシート一覧に戻る」、編集画面の「← レシート詳細に戻る」も共通の「戻る」ボタン（`BackLink`）にする。一覧から開いた詳細であれば1つ前に戻る（通信なし）。
- **見ていた行を開いた状態で戻る（必須要件）**：「詳細を見る」を押した瞬間に、一覧の URL に `open=行のID` を書き込んでから（`replaceState`、通信なし・履歴は増えない）詳細画面へ移る。一覧は `open` を現在の URL から読み、その行を開いてスクロールする。1つ前に戻った場合も、ブラウザの「戻る」の場合も、リンクで開き直した場合も、同じように行が開いた状態になる。

#### 5.5 アプリ共通の「戻る」ボタン（`BackLink`）

「アプリ内の直前の画面から来たときは1つ前に戻り、そうでなければ戻り先へのリンクとして開く」（スマホ向け Web アプリで一般的な作り。URL を直接開いたときにアプリの外へ戻ってしまう問題も避けられる）。

| 部品 | 役割 |
|---|---|
| `components/navigation/NavigationTracker.tsx` | 共通レイアウトに置く。画面の種類（パス）が変わる移動のたびに、移動先の履歴エントリのメモ（`history.state`）に「直前にいた画面のパス」を記録する。ブラウザの戻る・進む（popstate）のときは書き換えない |
| `components/navigation/BackLink.tsx` | 共通の「戻る」ボタン。直前にいた画面のパスが戻り先のパスと同じなら `router.back()`、それ以外は戻り先へのリンク |
| `lib/navigation/history-state.ts` | 履歴のメモの読み書きを集約。画面の状態を URL に反映する処理（分析画面・一覧）も、メモを消さない `replaceUrlKeepingAppState` を使う |

**リスクと備え**

- 履歴のメモは Next.js も内部で使っている。Next.js は `replaceState` を差し替えており、渡したオブジェクトに自分の項目をコピーしてから保存する（`app-router.js` の `copyNextJsInternalHistoryState`）。この動きに依存しているが、公式に案内された使い方ではない。
- 備え1：メモの読み書きは `history-state.ts` の1か所に集約し、他から `history.state` を直接触らない。
- 備え2：記録が消えた・読めない場合は「リンクとして開く」になるだけで、戻り先と状態は URL で保たれる（間違った画面には移らない）。
- 備え3：戻ったときに画面の部品が作り直され、URL から状態を読み直す前提（`cacheComponents` が無効）。`cacheComponents` を有効にすると、部品の状態が保持される動きに変わるため、見直しが必要。
- 備え4：Next.js を更新したときは、手動テスト仕様書の「Next.js 更新時の確認項目」を実施する。
